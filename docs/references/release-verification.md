# 构建与发版验证协议：摸底—拍板—坑—实测

> 摘要：构建发版类任务的栈无关方法论——摸底决定方案、决策点逐项拍板、坑表带排查手法、产物解包实测（不信文件名）。dijiang-finish-work 发布收尾、dj-gov 发版清单、version-management 的执行面协议。源出 go-release-workflow（Go/goreleaser 实战提炼，2026-11 融合，栈特定细节留在原技能）。

## 四段结构

### 1. 摸底先行（方案由现状决定，不先入为主）

- 依赖与工具链约束（交叉编译条件）、remote/tag 现状、版本号现有写法、**测试脚本完整性**——四者决定发版模式与配置形态
- 拿不准的一律进摸底清单，不带假设进实现

### 2. 拍板决策点（逐项确认，不默认）

- 平台矩阵（多配一个平台通常近零成本——按用户取舍而非拍脑袋全开）
- 发版模式：本地 snapshot vs 打 tag 正式发（两者的发布配置互斥，切换是显式动作）
- 版本注入方式：构建时注入（一劳永逸）vs 硬编码（每次手改必漏）
- 命令面规模：help/build/test/release/clean 最小集起步

### 3. 坑表模式（按踩坑顺序记，每坑四件套）

现象 → 根因 → 修复 → **排查手法（可复现的命令）**。通用排查纪律（不限栈）：

- **烂尾脚本假绿**：半成品 e2e 脚本退出码 0 但什么都没测——接进测试目标前先完整读一遍：日志行数与步骤数对不上、无终态断言输出即嫌疑；发现存量烂尾从测试目标摘掉、文件保留、上报拍板，不静默接入制造虚假信心（= evidence-gate「假完成」的测试面变体）
- **用户报的 bug 可能是 PATH 里的旧二进制**：源码已修用户仍报错——先 `which -a` + `--version` 对账定位实际运行的构建，旧报错新通过 = 根因是旧安装，修复是重装不是改码
- **构建链的静默状态污染**：看似无害的环境告警可能把元数据污染成空值（如版本名变 `none`）——产物名/元数据出现字面量异常值时查构建工具的 state 解析，`--verbose | grep` 污染现场

### 4. 解包实测验证协议（全绿才算完）

1. 配置合法性检查工具通过
2. 构建产物 `--version` 输出与预期格式对账（版本注入是否生效）
3. 测试目标先构建再测——**测新鲜二进制而非陈旧产物**
4. 产物数量 = 平台矩阵数
5. **解包实测（不要只看文件名）**：解包跑包内二进制 `--version`、`file` 查架构正确性、checksum 条目数对账
6. 命令面干跑（`-n`）正确

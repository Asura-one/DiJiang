# 设计决策

本文档记录 DiJiang 在纯 skill 架构（ADR-005）下的设计决策，为当前唯一有效版本。

## 1. 纯 Skill 无运行时

**决策**：所有工作流逻辑分散在 SKILL.md 文件中。无 CLI 二进制、无编译产物、不绑定任何特定 agent 平台。

**理由**：skill 本质是文本，agent 直接消费即可。去掉运行时层就同时去掉了构建、发布、PATH 依赖和平台适配的全部成本。

**权衡**：正确性依赖 agent 遵循文本纪律，无硬拦截。
**候选方案**：保留 CLI 二进制运行时。弃用原因：平台适配层维护成本高、运行时依赖限制 agent 选择，已由 ADR-005 明确迁移。

## 2. Bucket 分类

**决策**：技能库分为两个 bucket——engineering（41 个 skill）与 productivity（5 个 skill）。

**理由**：代码工作流与通用工作流分离，让各场景的加载清单更聚焦，避免无关 skill 稀释上下文。

**权衡**：跨 bucket 协作需要显式引用。
**候选方案**：单一扁平技能库。弃用原因：加载清单过长，且通用任务会暴露大量工程细节，噪音大于收益。

## 3. User-invoked vs Model-invoked

**决策**：user-invoked skill 只由用户显式触发（`disable-model-invocation: true`），负责编排与入口；model-invoked skill 可由模型自动触发。user-invoked 可调用 model-invoked，但永远不能调用另一个 user-invoked。

**理由**：编排型 skill 一旦被模型自发调用会跳步、绕过节流；入口保持人工控制，内部机制交给模型按需触发。

**权衡**：user-invoked 的自动化程度受限，需要用户显式启动。
**候选方案**：允许 model 自动调用所有 skill。弃用原因：编排入口被跳过会导致流程失控，与"门禁式纪律"目标冲突。

## 4. 战术路由 + 战略路由

**决策**：双路由并存——`dj-dispatch` 是逐请求的战术路由（一进一出），`dj-ask` 是全局的战略路由（flow 路径图：主流程、入口匝道、独立工具、词汇层）。

**理由**：单请求级调度需要快速确定性；全局路由需要解释 flow 全貌与分支选择。单一机制难以同时满足两者。

**权衡**：双路由带来职责重叠的风险。
**候选方案**：只保留 dispatch 式逐请求路由。弃用原因：缺少全局视角，agent 无法理解工作流全貌与可选路径，容易迷失在局部决策中。

## 5. 改码三明治护送

**决策**：`dj-regression-guard` 作为所有改码任务的前置纪律：改前基线 → 修改 → 专项验证 → 改后回归。它引用 `dj-fullstack-testing` 的机制但绝不复制。

**理由**：代码变更破坏现状的风险与变更规模无关，先锁基线再动手，才能断言"改坏了"还是"本来就有问题"。

**权衡**：多一轮基线运行，改码流程变长。
**候选方案**：改码后单独补一轮测试。弃用原因：无基线时无法区分回归与存量缺陷，回归保护名存实亡（ADR-006）。

## 6. 安全约束下沉为文本

**决策**：Route Gate / Git Gate / Capability Gate 从运行时硬编码下沉为 skill 文本纪律。

**理由**：没有运行时门禁可依赖，安全性必须由 agent 通过 skill 文本自觉执行，这是纯 skill 架构的必然推论（ADR-005）。

**权衡**：无结构性拦截，完全依赖 agent 遵循指令。
**候选方案**：继续运行时门禁。弃用原因：运行时已被删除，重造等于否定 ADR-005 的迁移前提。

## 7. CONTEXT.md 为领域术语唯一真相源

**决策**：所有 skill 统一使用 CONTEXT.md 定义的术语，确保跨 skill 一致；`dj-domain-modeling` 负责维护与演进。

**理由**：术语漂移是跨 skill 协作的第一杀手。单源真相保证任一 skill 的表述变化在全库自动对齐。

**权衡**：术语变更需经 dj-domain-modeling 流程。
**候选方案**：各 skill 自行定义术语。弃用原因：同一概念多种叫法，引用和检索全部失效。

## 8. ADR 记录难逆转决策

**决策**：只在三类情形创建 ADR：难逆转、缺背景会误读、真实权衡过时。当前生效：ADR-005（迁移纯 skill）、ADR-006（引入回归守卫）。

**理由**：ADR 的成本是维护，只有需要长期记忆支撑的决策才值得记录；琐碎决策记录即噪音。

**权衡**：难逆转决策若非 ADR 记录，后人只能从代码反推动机。
**候选方案**：全量记录每条决策。弃用原因：文档膨胀，关键决策被淹没。

## 9. 引用不复制

**决策**：skill 间共享机制只做引用，不内嵌副本——如 `dj-regression-guard` 引用 `dj-fullstack-testing` 的映射表与冒烟集。

**理由**：单源真相，被引用方更新自动生效；复制会让两份副本漂移，回归范围不再可信。

**权衡**：跨 skill 引用要求读者具备上下文。
**候选方案**：复制关键内容到使用方。弃用原因：双份维护点必然漂移，回归机制失去可信度。

## 10. Worktree-First 保留为文本纪律

**决策**：所有代码变更在独立 worktree 中进行，主工作区永远干净。此规则从早期 CLI 时代继承，作为 skill 文本约束继续生效。

**理由**：agent 编辑过程不可控（残留、半合并、测试产物），隔离 worktree 保证主 checkout 无论过程多乱都保持干净，且被本仓库的经验反复验证。

**权衡**：任务期间磁盘用量增加，跨分支上下文切换需显式操作。
**候选方案**：直接在主工作区改。弃用原因：回归验证时"干净基线"的前提被破坏，三明治纪律（决策 5）无从谈起。

# benchmark-checklist: 性能数字七问

来源：pstack benchmark-checklist 融合（2026-11）。凡产出性能数字——回归报告里的耗时对比、专项性能测试结论、优化前后、选型对比——**报告或据其行动前逐问过表**。每问要证据（一次真实运行的输出），不猜代码。

粗略估算（用户随口要个大概）只需 1 次运行，但必过第 4/7 问、并注明单次。**方案选型永远不是粗略估算。**

## 跑之前

- 先写下预期结论原话（如「60k 行导出 p50 快 30%」）——七问就是拷问这句话
- 读测量脚本，弄清它计时了什么、统计了什么、忽略了什么
- `uptime` 查负载、`nproc` 查核数；机器忙就说明，或 A/B 交替让两侧同噪声。测不出就明说

## 七问

1. **为什么不是 2 倍？** 说出限制器（limiter）：CPU profile / I/O 等待 / syscall 计数，映射到源码。压测工具先饱和 = 测的是工具本身。改动没动数字 → 先找限制器再下「无用」结论
2. **调优了吗？** 两侧都按生产形态跑（release 构建、生产参数、缓存冷热、同版本同数据）。一侧跑默认配置 = 比较的是配置不是实现；限制器是可调参数（逐行 commit/debug 构建/缺索引）→ 先调平再选优；调不平就没有赢家
3. **破极限了吗？** 做算术：字节速率对磁盘带宽、OPS×单耗时对核数、节省时间对被改部分占比（占 10% 运行时的优化最多快约 11%）。超出物理极限的数字测的是缓存/op/bug
4. **报错了吗？** 统计失败与非成功响应数（拒绝都很快，超时很慢）；校验输出**正确**而非仅存在。脚本不数错误就加上
5. **可复现吗？** 每侧 ≥5 次交替跑（A,B,A,B），报中位数与区间；差距小于波动区间 = 无可测差异，临界用秩和检验
6. **相关吗？** 微结果旁边量端到端路径（真实数据量+并发），报微结果占比。占请求 1% 的优化最多让请求快 1%
7. **真的发生了吗？** 确认工作发生在计时区间内：请求到达、行写入、结果被使用。惰性求值（没人迭代的生成器、没人 await 的 promise）与超时都会产出「没发生的数字」

## 报告格式

- 结论先行：更快/更慢/无可测差异/** inconclusive**（说不出限制器、有侧未调平、来不及查 4/7 问 → 必须标 inconclusive 并点名缺口，不硬下结论）
- 数字带单位、次数、区间、限制器（例：「p50 41ms→33ms，每侧 7 次中位数，后侧区间 32-35ms，单核 JSON 解析限制」）
- PR/报告正文只放一个主数字，全程数据在链接的产物文件

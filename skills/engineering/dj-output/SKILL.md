# Output: 创建和维护项目文档

## 职责

创建和维护 PRD、设计文档、决策记录。文档与代码双向对齐——代码改则文档改，文档改则代码改。

## 主流程

### 1. 收集信息（PRD）

写 PRD 前确认足够信息：
- **目标** — 要解决什么问题？
- **用户** — 谁会使用这个功能？
- **方案** — 确认了哪个方向？
- **约束** — 技术/时间/兼容性限制？

如果关键信息缺失，不编造——留 `TBD` 标记并注明需要谁确认。仅靠一句话请求时，先列 3-5 条假设补齐再写，不靠大量 TODO 占位。

### 2. 选模板并编写

- 写 **PRD** → 用下面的 PRD 模板
- 写 **设计文档/决策记录** → 用下面的设计文档模板
- 写**执行计划** → `{task_dir}/implement.md`

聚焦 User Stories 和 Acceptance Criteria 的独立可验证性。

### 3. 对抗式自审

写完文档后自问：
- 每个 User Story 是否独立可验证？
- Out of Scope 是否明确到不会产生误解？
- Acceptance Criteria 是否有人能实际执行验收？
- 读者能理解我为什么做了这个决策吗？

### 4. 核对代码一致性（文档类必做）

文档涉及现有代码时，逐项**核对符号与引用是否存在**，不以"看起来对"或"模块里有相近函数"为准：

- 对代码里每个 `import X` / `X.y` / `from A import B`，在模块文件里**确认 `X`/`B` 这个符号真的存在**（用 grep 或读文件核对名字，而非只读说明）
- 例：`from modules import notify` 要求 `modules` 里有 `notify` 符号；若 `modules` 只有 `send` 而 `notify.send` 仍被调用 → **命名不一致**，如实记录，不声称"与代码一致"
- 例：`def run(): return notify.send("hello")` 而模块里没有 `notify` → 该调用是悬空引用，文档必须标注

发现不一致时：写进文档"已知不一致"段 + 给对齐方案，不擅自改代码。

### 5. 保存

- PRD 存 `{task_dir}/prd.md`
- 设计文档存 `{task_dir}/design.md`
- 执行计划存 `{task_dir}/implement.md`
- 建议下一步：PRD 加载 `dj-split` 拆分

## PRD 模板

```markdown
## Problem Statement
<要解决的问题，从用户视角描述>

## Solution
<方案概述>  // 一句话说清楚做什么

## User Stories
- As a <角色>, I want <功能> so that <价值>

## Implementation Decisions
- <重要的技术选型和理由>
- <不需要写全部细节，只写关键取舍>

## Testing Decisions
- <测试策略：手动/自动、E2E/单元>

## Out of Scope
- <明确不包含的能力>

## Acceptance Criteria
- <可验证的验收条件，每条独立可测>

## Notes
<补充信息、已知风险、待确认项>
```

## 设计文档模板

```markdown
## 背景
<为什么需要这个设计>

## 方案
<做了什么设计决策、取舍理由>

## 影响范围
<影响的模块/接口/数据模型>
```

## 对抗式审查

写完文档后，自己提问：
- 我有没有隐瞒任何不确定的地方？
- 读者能理解我为什么做了这个决策吗？
- 遗漏了什么边界场景吗？

## 文档与代码对齐

- 文档涉及现有代码时，按主流程「步骤 4 核对代码一致性」逐项核对符号存在性
- 代码改完 → 重新读代码本身核对关联文档是否需要更新，不凭记忆或旧认知
- 文档改完 → 标注代码中需要变更的部分
- 双方不一致时以代码为准，但必须更新文档标记已过时
- 🔴 **发现代码内部不一致（引用符号缺失、命名不符）时如实记录并给对齐方案，不声称"与代码一致"**。隐瞒不一致 = 文档失效。

## 失败模式

| 触发条件 | 一线修复 | 仍失败兜底 |
|---|---|---|
| 关键需求信息缺失 | 留 `TBD` 并注明需谁确认 | 停下，不编造补齐 |
| 文档与代码已不一致 | 以代码为准，标文档过时 | 停下请用户确认哪边为真 |
| PRD 验收标准无法执行 | 改写为可执行断言 | 标「验收待定」，交 `dj-grill` |

## 反例

| ❌ 不要做 | ✅ 正确做法 |
|---|---|
| 文档写完美再给用户看 | 先写草稿，确认方向再完善 |
| 文档和代码互相矛盾 | 改了一方就改另一方 |
| 文档写得太技术 | 面向读者（PM、新人）写 |
| 编造缺失的需求信息 | 留 `TBD` 标记 |
| PRD 写成技术设计文档 | 聚焦用户问题和行为 |
| 直接从对话跳到实现 | 先出 PRD → 拆分 → 再实现 |

## Hard Rules

1. 先写草稿再完善——不追求一次完美
2. 改了一方代码就改另一方的文档（或标明已过时）
3. 双方不一致时以代码为准，但必须标注文档已过时
4. 面向读者写——PM 看 PRD、开发者看设计文档、新人看 README

参考规范：`references/doc-template.md`（文档模板标准框架）；产出 API 接口文档时另用 `references/api-doc-template.md`（六段最小结构，示例优先）。

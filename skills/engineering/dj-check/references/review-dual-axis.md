# PR/分支审查档（双轴纪律）

> 由 dj-review 并入（DJ-013）。check 第 5 档内核——两个独立维度分别审查后汇总，防互相污染。

## 双轴定义

- **轴 A — Spec 匹配度**：diff 是否忠实实现源需求（PRD/issue/spec）。报告遗漏的行为、超出范围的新增、与 spec 矛盾的设计
- **轴 B — 代码质量**：diff 内部质量。与项目现有模式的偏差、过度工程/过早抽象、潜在缺陷（空指针/资源泄漏/并发）、风格不一致

两轴输入与发现**保持独立**——子任务不互相引用，各自汇报。**checker 不读 maker 的完成自述**：审查输入只取 spec + diff + 测试结果，不读实现者的推理链/总结/自评（why：拿着 maker 的叙事，checker 会复述叙事而不是独立验证——Maker-Checker 分离的关键在信息边界，不只是角色分离）。平台有并行执行能力时并行跑两轴；没有时串行，但不得因缺工具省略任一维度。

## 发现先复核再入清单

每条发现是**待验证命题**，不是事实。入问题汇总前先做一次反驳复核：

- 回读发现所引的真实代码，确认问题**当前存活**：不是别处已处理、不是 by-design、不是把潜在风险写成活跃 bug。
- 直读即溶解的发现（按名字推断、只看部分上下文）无论谁提出都降级为 FYI 或删除——并行审查者按名字推断导致过度报告是已知失败模式。
- 误读契约的发现**先修契约描述再重审**，不要直接按发现改代码。
- 复核结论分四类：契约误读 / 有效须改 / 有效但属权衡（显式记录成本）/ 噪音。审查最多 3 轮；3 轮后仍有实质发现说明产物没 ready，上报用户，不磨第 4 轮。
- 可检失败信号：连续两轮有实质发现、却一条都没被判为须改 = **doubt theater**（在验证不在怀疑），停下来重新对齐问题。

## 严重度四档

| 档 | 含义 | 处置 |
|---|---|---|
| **阻塞** | 必须改，否则不放行：正确性、安全、数据损坏、spec 明确违背 | 修完复扫 |
| **应改** | 本任务内改：违反项目现有模式，或留下明显维护负担 | 修完复扫 |
| **可忽略 Nit（Nit）** | 作者可决定是否改：风格偏好、命名口味 | 记录，作者拍板 |
| **背景 FYI** | 只需知道，不需动作：取舍说明、相关但超范围 | 记录 |

只有阻塞与应改进阻塞清单；Nit 与 FYI 不许写成「必须」。判不准是应改还是 Nit 时，按「不改会不会在两周内造成真实故障」判。

## 结构问题要给命名动作

报结构 / 复杂度问题时必须给出**有名字的重构动作**，不能只描述不舒服：

- 条件链 / 布尔参数堆 → 改成 typed model、dispatcher / 策略表
- 同一形状假设重复出现 → 提到单一结构里（generated column / 基准表 / 常量）
- 抽象只服务一个调用者 → 删掉抽象，而不是抛光它
- 层数过多 → 数层与隐藏状态，折叠单调用者包装
- 状态散落 → 收进 reducer / 状态机

给不出命名动作的结构抱怨按 Nit 处理。

## 审测试靠实验，不靠读

测试是否真的锁住行为，用一次突变验证：反转本次改动新增的一个条件（去掉取反、`&&` 换 `||`），跑套件，再还原。**保持绿的突变就是发现：点名缺失的测试用例**。测试只断言实现细节（内部调用次数、私有结构）同样是发现——断言应落在使用者能观察到的行为上。

## 流程

1. 准备：`git diff --stat HEAD` + `git log --oneline -5`，确认变更范围与 PRD/issue 引用
2. 独立审查（两轴分别执行，只输出问题清单不修改代码）
3. 汇总为一份报告（模板见下）

## 汇总模板

```text
## 审查：<变更描述>
- Spec 匹配度：<通过/有问题>
- 代码质量：<通过/需改进>
- 安全性：<人工审阅重点，如涉及>
- 问题汇总：
  1. [阻塞] <问题描述>（来自：Spec/质量）
  2. [应改] <问题描述>
  3. [Nit] <问题描述>
  4. [FYI] <问题描述>
- 结论：<通过 / 需修改 / 需重新审查 / 证据不足>

结论四态：前三态沿用；**证据不足**（inconclusive）= 测了但无法判定（样本不足/覆盖盲区/结果矛盾）——如实写优于硬凑通过，权威定义见 `references/evidence-gate.md` 结论三态。
```

## 边界

- 不做深度架构评审——那是 `dj-audit`（历史考古/反模式）/ `dj-reason` 的职责范围
- 不引入 reviewer 自己的风格偏好——按项目现有模式判断
- 报问题必附建议方向——只报问题不改建议，reviewer 就没有价值

## 判例

| 情形 | 处置 |
|---|---|
| 无 PRD/issue 可对照 | 标注「无源可对照」，只跑质量轴 |
| 变更过大一次审不完 | 按文件/模块分批审，标未审范围 |
| spec 与实现严重冲突 | 报告冲突点，请用户裁决，不改码 |
| 发现的问题修复后 | 修复后重跑增量复扫（防修旧引新）；复扫范围至少覆盖修复点直接触及的文件 |

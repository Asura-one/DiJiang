| 项目 | 内容 |
|---|---|
| **Outcome** | 改码任务被三明治回归协议护送：改前基线、专项验证、改后回归、归因结论 |
| **Done when** | 改前基线快照 → 专项验证通过 → 改后回归无新增失败（或已按 S4 处置） |

# Regression Guard: 改码三明治回归协议

对每一次代码修改任务执行"三明治"护送：**改前基线 → 修改 → 专项验证 → 改后回归**。目标是让改码行为始终处于回归保护之下——新改动生效与否、旧功能是否被破坏，两件事都有测试背书，而不是靠"没报错"的直觉。

本技能是**任务级轻量协议**。全面回归测试（全功能枚举、UI/UX 评估、契约校验等重武器）由 `dj-fullstack-testing` 承担，本技能只引用其机制、不复制、不改动它。

## 模式路由（进入本技能先做此判定）

| 场景 | 判定 | 走向 |
|------|------|------|
| 接到改码任务（修复 bug / 新增功能 / 重构），需要改前后的回归保护 | **三明治模式** | 在本技能内按 S0–S6 执行 |
| 用户要求全面 / 系统 / 全量回归测试，或任务结束后的全量验证 | **全量模式** | 转交 `dj-fullstack-testing`，本技能不重复执行 |
| 仅讨论测试方案、分析测试结果，不涉及改码 | 不适用 | 直接回答，不启动协议 |

拿不准时选三明治模式——它便宜；全量模式的成本由 `dj-fullstack-testing` 的流程决定，不在本技能内打折执行。

## 协议流程

### S0 · 快速层定义（每个项目首次任务付一次成本，之后复用）

"快速层" = 本次任务改前/改后要双跑的测试子集，目标耗时 < 3 分钟。按顺序判定：

1. 项目有冒烟标记（pytest `@pytest.mark.smoke`、`npm test -- smoke` 等）→ 只跑标记子集
2. 无标记 → 按 `dj-fullstack-testing` 步骤 0.1a 的变更文件→受影响模块映射表，圈定受影响模块的测试 + 该技能步骤 3a 的冒烟最小集
3. 项目无任何测试基建 → 走"零基建退路"（见下节），不同时执行本步骤

选法持久化：将"本项目的快速层怎么选"写入 `dj-fullstack-testing` 维护的 `docs/project-understanding.md`（追加"快速层定义"一节）。后续任务直接复用，仅在基础设施文件（package.json / Cargo.toml 等）变更时重新判定。

**超时降级**：S1 执行时若快速层实际耗时超过 3 分钟 → 收窄为"冒烟最小集 + 本次任务直接触及模块的测试"两块，并将实际选用的子集记入基线快照（S3 改后回归跑同一子集，保证可比）；若收窄后仍超 3 分钟，保留该子集并在任务报告中标注"快速层耗时异常，建议拆分测试或加冒烟标记"，不阻塞协议。

### S1 · 改前基线

1. 执行 `git log -1 --format=%H` 记录当前 commit-id
2. 跑快速层，将结果快照落盘 `.temp/regression-baseline-<时间戳>.json`：commit-id、测试清单、逐项 PASS/FAIL、耗时
3. **允许基线是红的**：已有失败记入"已知基线失败清单"，不阻断改码；后续比对采用**增量对比**——只关心改后是否出现基线之外的新增失败
4. 快照生命周期 = 本任务。任务结束即失效删除，不持久化到 docs/

**🔴 CHECKPOINT · 🛑 STOP（冒烟全红）**：若 S1 阶段就发现快速层全红（连冒烟都过不了），停止协议并向用户报告：先处理阻断性问题，改码没有意义。未报告用户不得继续任何改码步骤。

### 改码执行（协议包住 TDD，不是替代）

- 改码入口照常走 `dj-implement` / `dj-tdd`，本技能不接管编码
- **TDD 红测兼任本次任务的专项测试**：bug 修复先写失败测试（复现 bug），功能新增先写验收测试
- 粒度 = 逻辑任务级：任务内多次编辑**不重复**跑回归，只在任务结束时执行一次 S3

### S2 · 专项验证（先行，便宜、归因清晰）

改码完成后，**先跑专项、再跑回归**：

- bug 修复：红测转绿 = 修复生效
- 功能新增：验收测试通过 = 功能生效
- 专项测试失败 → 修复本身没生效，回到改码，此时**不要**跑 S3（回归没意义）
- 专项通过才进入 S3

专项与回归失败的归因是分离的：专项挂 = 改错了；回归挂 = 改多了波及别处。两类失败的修复动作不同，不得混为一谈。

### S3 · 改后回归

1. 先校验 `git log -1 --format=%H` 与基线快照中的 commit-id 一致性：若中途发生其他提交（基线过期），重跑 S1 生成新基线再继续
2. 重跑快速层
3. 与改前基线逐项 diff：基线内已知失败保持失败 → 不算回归；基线外的新增失败 → 进入 S4
4. 基线内已知失败转绿 → 顺带修复，记录在任务报告中（不作为放行条件）

### S4 · 新增失败处置

按序执行，每步失败才进入下一步：

1. **基线 diff 滤噪**：确认失败不在已知基线失败清单内
2. **flaky 重试 ×1**：单独重跑该测试一次，通过则标记 flaky 并放行（记录在案，连续两次任务出现同一 flaky 项时建议隔离修复）
3. **自动修复 ≤ 2 轮**：定位原因并修复代码，重跑 S3。两轮仍失败则停
4. **🛑 STOP · 回滚 + 报告**：回滚本次修改，保留失败现场（测试输出、复现命令），向用户报告"改动导致回归，已回滚"，不得静默吞掉。**回滚后必须等待用户裁决下一步方向，不得自行重新改码**

**铁律：任何情况下禁止通过修改、删除、跳过失败的测试来让回归变绿。** 测试文件自身的问题（断言过时、依赖环境变化）必须显式标记、单独说明，交由用户裁决，绝不静默处理。

### S5 · 全量层建议（🔴 CHECKPOINT · 决定权在用户）

任务级改动波及面大时，主动建议（不代替决定）跑全量：

- 触发条件：diff 触及 P0 范围——路由定义、依赖清单（package.json / Cargo.toml / requirements.txt）、公共工具库（src/utils / src/lib）、数据库 schema
- 建议话术需包含波及面证据（改了什么、按 `dj-fullstack-testing` 0.1a 映射影响哪些模块）
- **🛑 用户未答复前不得自行启动全量测试，也不得视为默认同意**；用户同意 → 转交 `dj-fullstack-testing` 执行全量模式；不同意 → 记录在任务报告，协议到此为止

### S6 · 测试债台账

- 每个走过"零基建退路"或补全不完整的任务，将欠账记入 `docs/testing/test-debt.md`：模块名 | 欠账内容（无测试 / 测试不全）| 建议补全方式 | 记录日期
- 台账**非阻塞**：不阻止任务完成，但每次任务开始时检查台账，若本次任务恰好触及欠账模块，则按"零基建退路"的同步补全规则顺带偿还该模块
- 向用户汇报任务时，若台账非空，附一句当前测试债概览

## 零基建退路（项目没有测试套件时）

1. **基线退化**：S1 的快速层退化为冒烟级检查——服务能启动、健康检查端点返回 200、核心入口页面能打开（复用 `dj-fullstack-testing` 步骤 3a 的冒烟最小集）
2. **专项强制 TDD**：bug 修复必须先写失败测试——这个测试本身就是该模块的第一块测试资产
3. **模块级同步补全**：为本次任务涉及的模块生成测试（枚举该模块功能点 + 生成用例，参照 `dj-fullstack-testing` 步骤 1 的枚举方法，但范围仅限受影响模块）。全库级套件补全不做同步阻塞，记入 S6 台账由后续任务逐步偿还
4. **复利效应**：每个任务沉淀的专项测试逐渐累积为该项目的回归套件，零基建项目随用随建

## 与其他技能的边界

| 技能 | 分工 |
|------|------|
| `dj-implement` / `dj-tdd` | 改码与红绿循环的执行者，本技能只做护送（基线/回归/归因），不接管改码 |
| `dj-hunt` | bug 排查与修复者。Hunt 定位根因后，修复的回归保护由本协议承接；反之本协议 S4 的"自动修复"归 hunt 纪律管 |
| `dj-fullstack-testing` | 全量回归引擎。本技能引用其三处机制：步骤 0.1a 的 diff→模块映射表、步骤 3a 的冒烟最小集、`docs/project-understanding.md` 文档格式。**引用不复制**——上述机制以 `dj-fullstack-testing` 文本为准，本技能不内嵌副本，其更新自动生效 |
| `dj-check` | 交付质量门禁（改码结束后）。与三明治协议的改前/改后回归互补：本协议护改码过程，dj-check 护交付收口 |

## 任务报告要素（协议执行完毕后向用户汇报）

- 基线状态：commit-id、快速层构成、已知基线失败数
- 专项结果：红测转绿 / 验收通过与否
- 回归结果：新增失败数（应为 0）、flaky 项、顺带修复项
- 处置记录：若触发 S4，写明走到了哪一步
- 建议与欠账：S5 是否建议全量、S6 台账当前概览

## 反例（禁止行为）

| # | 反模式 | 后果 |
|---|--------|------|
| 1 | 跳过 S1 基线，只做改后回归 | 改后失败无法区分"我改坏的"和"本来就坏的"，归因失效 |
| 2 | 绝对绿灯要求（基线红了拒绝改码） | 存量项目几乎必然死锁，协议被执行成本杀死 |
| 3 | 改测试让回归变绿 | 铁律违反。测试问题必须显式标记说明 |
| 4 | 任务内每次编辑都跑双回归 | 耗时翻倍拖垮迭代，粒度 = 逻辑任务级 |
| 5 | TDD 豁免三明治 | TDD 保证新功能有效，对回归是盲的，S3 一步不能省 |
| 6 | 专项和回归混跑、失败混报 | 两类失败归因不同，混报后修复方向不可判 |
| 7 | 基线快照持久化到 docs/ | 基线只服务本次任务，过期快照是噪音 |
| 8 | 零基建项目同步补全全库套件 | 修 bug 5 分钟、补套件 2 小时，agent 会悄悄绕过协议 |

## Hard Rules

1. 改码任务默认触发三明治协议，S0–S6 不可跳步（跳过必须显式说明理由）
2. 改前必须记录基线；无基线不得声称"回归无新增"
3. 禁止改/删/跳测试让回归变绿——测试问题显式标记，交用户裁决
4. 专项未通过不进 S3；S3 有新增失败必须走 S4 处置
5. S5 全量层：用户未确认绝不自行启动
6. 回滚后必须等待用户裁决，不得自行重新改码

## Gotchas

| Gotcha | 后果 | 预防 |
|--------|------|------|
| 基线过期还跑回归 | 归因失真 | S3 先校验 commit-id |
| 基线全红仍直接改码 | 改码无意义 | S1 冒烟全红先 STOP |
| 基线快照存到 docs/ | 过期快照成噪音 | 快照生命周期=本任务 |
| 混跑专项与回归 | 归因不可判 | 专项先行，回归后行 |

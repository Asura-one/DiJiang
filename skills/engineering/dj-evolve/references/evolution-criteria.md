# 升格判据细化：阴性知识、复现门槛与候选字段

> 摘要：dj-evolve 判据筛选与候选展示的细化规则——阴性知识挖掘、复现门槛、反例与停止条件必填、存量体检。权威判据仍在 SCOPE.md，本文只做执行细化。

## 1. 阴性知识作为升格原料（第五类挖掘信号）

- 扫描候选时**必须查** `.dijiang/memory/` 中 `kind=negative` 的条目：死路、失败尝试、被否决的路线——失败经验的复利常高于成功经验。
- **分层纪律**：死路本体留记忆层（它描述「这个世界是什么样」）；技能层只升格「如何避免」的可操作规避（它描述「下次怎么做」）。例：记忆存「方案 X 在 exFAT 上必挂」，技能升格的是「构建前查文件系统支持符号链接」。
- 与 SCOPE「只增不删」的张力处理：记忆层阴性条目永不回滚（历史事实）；技能层不为死路建条目——只写规避。

## 2. 复现门槛（防单例噪音）

- 单次出现的经验**不提候选**，暂存 dj-memory 标待验证。
- 同一模式**第二次复现**才允许提候选（参考实践：momo-code 同一模式 ≥3 次才提炼 tactic——次数是设计选择不是普适值，取精神不取数）。
- 例外：带强证据的纠正（用户显式纠正 + 机制清晰可复述）可首现提候选，但必须标注「单例 + 强证据」。

## 3. 候选必带字段（行为合同）

每个候选展示时四字段齐全，缺一不提案：

| 字段 | 回答什么 |
|------|---------|
| 反例 | 这条规则的适用性何时失效？（边界情形） |
| 停止条件 | 什么信号出现时该放弃这条规则、交还人工？ |
| 复现次数 | 第几次出现？（单例需补强证据说明） |
| why | 规则存在的理由——缺 why 的规则是自进化时代第一批被「聪明」放宽的承重墙（anti-patterns #24） |

## 4. 验证纪律补充

- **验证集过拟合**：behavior-cases 通过数上升但真实会话表现无变化 → 怀疑案例集被候选「应试」，补真实场景案例再验。
- **致胜工具归因**：候选捆绑多个改动时只认最终致胜的那个——「常出现」≠「有贡献」，无法归因就拆成单候选。
- **口径冻结**：差分验证前先声明对照集身份（behavior-cases 版本 / 判定标准 / 模型与平台版本）。比较对象没冻结时，先怀疑「比错了东西」再怀疑候选——2026-11-18 三向合并误删的根因就是把 base 设成 HEAD，比较对象错位。
- **逐 case 归因优先于泛扫**：拿具体失败案例生成定向改动，父子版本按**每个 case** 比较（不看平均分）；父严格支配子则不入池，互不支配的互补候选保留待并。平均分掩盖「修好一个、弄坏一个」。
- **单候选单边界**（SKILL.md 外溢）：一个候选只动一个文件/一个技能；跨多边界的改动拆成多候选独立评估——可审计、可公平比较。

## 5. 存量体检（skill-doctor）

dj-evolve 常规轮次之外，可对单一技能做健康体检——**只看失败会话**（成功会话无信息量）：

- 收集该技能近 N 次触发中未命中/路由错/执行失败的会话
- 四维评分：触发精度（误路由率）/ 执行质量（失败率）/ 覆盖完整（description 承诺 vs 实际做到）/ **接受率**（输出被用户直接采用，还是被改掉或重做）。另加一条硬信号：**长期从未触发的技能 = 路由盲区或退休候选**，逐个给判据（触发词写得太窄 / 能力已被别的技能覆盖 / 本就不该存在）。
- 产出：修补候选（走常规差分流程）或退役提案（走 SCOPE 退役政策）

## 6. 多视角评审（大 session 升级，SKILL.md 外溢）

**session 大或经验密度高时升级多视角评审**：spawn 三个并行只读评审子代理，各用一付透镜找候选——判断力透镜（决策质量/边界案例）、工具链透镜（工具错误/流程浪费）、发散透镜（被忽略的可能性/反直觉发现）——单 agent 自扫有盲区，三透镜交叉显著降遗漏；小 session 直接自扫不硬派。

## 7. 五类挖掘信号总览（SKILL.md 外溢）

五类挖掘信号：重复人工纠正 / 稳定成功的长流程 / 高频工具错误 / 反复查询的外部知识 / **阴性知识**（dj-memory `kind=negative` 的死路与失败——技能层只存「如何避免」，死路本体留记忆层，分层纪律见第 1 节）。

候选展示格式（SKILL.md 外溢）：**反例与停止条件**（适用性何时失效 / 何时交还人工）+ **复现次数**（单次出现只暂存，第二次复现才提候选）。

## 8. 升格五问（SCOPE.md 执行版，SKILL.md 外溢）

- 它未来还会跨任务重复出现吗？
- 带明确的做事方法吗（不只是观察）？
- 写进 skill 比留在 memory 更省 token 和错误率吗？
- 有验证基础吗（未验证的先暂存 dj-memory 标待验证）？

# 能力落层选型矩阵：最低权限层原则

> 摘要：一个能力该落在 prompt 模板、skill、script 还是 tool 层——判定原则是用能形成确定性闭环的最低层；新建技能前的第一道自查。

## 原则

DiJiang 的三层物理载体（SKILL.md / references / scripts）+ 平台侧的 prompt 与 tool 共同构成能力落层候选。**能形成确定性闭环的最低层优先**：层越低，验证越便宜、漂移面越小、复用越确定。

## 选型矩阵

| 层 | 载体 | 何时选 | 何时升层 |
|----|------|--------|---------|
| **L1 Prompt 行** | 一次对话内的一句话指令 | 用一次，无复用预期 | 第二次重复解释同一纪律 → 考虑 skill |
| **L2 Skill 正文** | SKILL.md 判例行 | 需要跨任务纠偏模型默认行为 | 判据需要数据/表格支撑超体量 → 拆 references |
| **L2.5 references** | 条件加载的深度文档 | 主文件放不下的论证/模板/清单 | 被多个 skill 共读 → 升 docs/references |
| **L3 Script** | scripts/ 确定性验证脚本 | 规则可用代码判定（体量/命名/拓扑） | 判定需要运行时状态 → 不落库，交平台 |
| **L4 Tool/运行时** | 平台能力 | 需要 hook/调度器/进程 | 纯 skill 库**永不落此层**（ADR-005） |

## 落库前自查（SCOPE 前置过滤）

1. 这个能力 prompt 一句话能解决吗？→ 能就不建载体
2. 它是「怎么做的方法」还是「一次性的事实」？事实进 memory，方法才考虑 skill
3. 它能用脚本确定性判定吗？能 → 脚本 + 一行 skill 引用（脚本管判定，skill 管何时跑）
4. 需要运行时吗？需要 → 出库，进 .out-of-scope 登记

## 反例

| ❌ | why |
|----|-----|
| 为单次任务写 skill | 单例噪音——先 memory 暂存（dj-evolve 复现门槛） |
| 把可脚本化的规则写成散文判据 | 散文会漂移，脚本不会——verify_skills.py 先例 |
| 为平台 hook 能力建 skill 载体 | 纯 skill 库无运行时，写出来就是纸面规则 |

# 放行申请（给拍板用的三段式）

> 摘要：合并 main、推 origin、live 同步、部署——这些动作要人点头。点头的人需要的是「改了什么、证据在哪、赌多大」，不是一份 diff。三段式：Summary / Evidence / Merge Danger。
>
> 来源：mattpocock/skills `pr`（MIT，转自 Humanlayer show-me 模板）；DiJiang 版并入放行动作。

## 什么时候写

每个需要用户放行的动作写一份，放在回复里（不需要单独建文件）：

| 动作 | 为什么需要 |
|---|---|
| 合并到 main | 受保护分支，合并即改变所有人的基线 |
| 推 origin / 远端 | 对外可见，撤回要强推 |
| live 同步 | 覆盖用户生效面，错版本会静默生效 |
| 部署 / 重启服务 | 影响线上，回滚有窗口 |
| 删除 / 覆盖 | 不可逆 |

## 三段模板

```markdown
## Summary
<最小可视化：伪代码 / 调用树 / 组件树 / 浅文件树 / 关键 diff 片段>

## Evidence
- **Before:** <截图 / 失败测试输出 / 旧行为证据>
  **After:** <截图 / 通过测试输出 / 新行为证据>

## Merge Danger
**Door:** <one-way / two-way>
**Blast Radius:** <一个词>
<可选：若合入，最坏会怎样；回滚怎么做>
```

## 逐段要求

**Summary**：选能说清关键点的最小视图。逻辑改动用伪代码或调用树，结构改动用文件树，UI 用前后截图。不要把整个 diff 贴上来——放行的人读的是形状，不是每一行。

**Evidence**：Before/After 成对出现。只有 After 不算证据（证明不了变化）；只有 Before 也不算（证明不了修好）。证据等级参考 `dj-check/references/delivery-risk.md` 的 L1–L5，至少到 L4（可重跑的命令输出）。

**Merge Danger**：

- **Door（单向门 / 双向门）**：回滚便宜的改动是双向门（合并后发现问题 revert 即可）；改变数据形状、对外契约、不可逆迁移是单向门（合了就得往前走）。拿不准按单向门处理。
- **Blast Radius（一个词）**：`local`（只影响本仓）／`team`（影响同仓其他人）／`service`（影响线上服务）／`data`（影响真实数据）／`users`（影响终端用户）。一个词逼你想清楚最坏波及面。

## 纪律

- 三段写不完整（尤其 Door 与 Blast Radius 说不清）= 这次改动还没准备好放行，先补证据或缩小范围。
- 放行申请**不构成授权**：用户看过之后说「可以」，才是授权；申请本身只是把决定变得可做。
- 一次申请只覆盖一个动作与一个范围；换动作（比如合并后又想部署）重新写、重新确认。
- 与 dj-git-guardrails 的分工：guardrails 管「这动作危不危险、该不该拦」，本文件管「怎么把决定呈现给人」。

# dj-remix 输入处理与补全流程

本文件承载 Phase 0 输入来源的详细处理方式，以及「本地已有不完整复刻项目」特殊情况的全套调整流程。SKILL.md 保留判定要点；执行对应场景时读本节。

## 1. 输入来源的详细处理（Phase 0）

**有可访问的 URL**
用 `fetch_content` 抓取，不要只看首页——列出能找到的所有关键路由/页面分别抓取。单页应用可能需要多抓几个状态（比如登录前/登录后能看到的内容不同）。

**有截图或设计稿**
用 `read` 逐张仔细看。**截图天然是静态快照，看不到 hover、动效、报错提示、加载状态**——这些要主动向用户问清楚，不要靠猜测补全；猜出来的交互往往就是后续被吐槽"复刻得不对"的地方。

**只有关键词/产品名（无 URL 无截图）**
先确认这个关键词具体指向哪个产品——如果有歧义（同名产品、或只是泛类目描述，比如"一个类似小红书的社区App"这种没点名具体产品的），跟用户确认清楚指的是谁，不要凭第一反应认定。确认后用 `web_search` 找官网/应用商店页面，能拿到 URL 就用 `fetch_content` 抓；抓不到网页内容（纯原生 App）或没有官网，就用截图搜索找界面截图，再搜几篇产品评测/功能介绍类文章补充截图里看不到的交互逻辑。

**关键词是信息量最少的起点，越是这种情况越要主动多做几轮调研**，而不是因为信息少就跳过调研直接凭印象开始列清单——信息不够时最容易脑补，这恰恰是漏功能的重灾区。这一步做的调研本身也是在为 Phase 1 攒素材，不算额外功夫。

**混合出现**
优先用信息量更大的来源（URL/搜索到的官网）补全信息量较小的来源（截图/关键词）看不到的部分。

## 2. 特殊情况：本地已有一个不完整的复刻项目

这种情况不能当成"从零开始"处理，也不能只看现有代码就假定复刻范围到此为止。按下述调整流程走：

1. **先摸清现有项目实际情况**：浏览项目结构，看已实现哪些页面、组件、功能——这是为了后面做对照，**不是**为了拿它确定复刻范围边界。
2. **仍然独立、完整走一遍 Phase 1**：针对**原始复刻目标**（原网站/App 本身）重新做完整拆解，不依赖"现有项目已做了什么"反推范围。这是最容易踩的坑：只在现有项目的认知边界内查漏补缺，那些原本被忽略、从未实现过的功能永远不会被发现——它们压根不在"已有项目"这个参照系里。这正是当初复刻不全面的原因，重复同样的方式只会得到同样的结果。
3. **做一次对照**：Phase 1 完整清单和现有项目逐项比对，标三种状态——已完整实现 / 部分实现（阉割版，如只做了默认状态没做报错和空状态）/ 完全没做。
4. **Phase 2 呈现差距清单**：不是从头开始的完整清单——问用户缺失项是否都要补，还是当初有意精简、不需要补。
5. **Phase 3 只补差距**：已完整的部分不动，只实现缺失/阉割部分；补的时候跟现有代码的写法、组件结构、命名习惯保持一致，除非用户明确想重构。
6. **Phase 4 先检查现有项目有没有做过差异化改造**：完全没做过则仍要走这一步，不能因为任务是"补全"就跳过；已做过则新补部分要匹配现有差异化风格（配色、版式语言），避免新旧部分气质不统一、看起来像拼凑。
7. **Phase 5 照常做最终自查**：交付说明里注明这次是"补全"性质，列清楚哪些是新增、哪些是原有的。

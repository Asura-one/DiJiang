# Remix: 网站/App 复刻与差异化改造

## 要解决的问题

"边看边写"几乎必漏——注意力被主视觉吸引，次要功能、边缘状态（空/加载/报错/禁用）、隐藏交互很容易被忽略，产出"看起来像"但覆盖不全的阉割版。复刻得"太像"还有版权/商标风险，也没体现使用者调性。所以走五步：确认范围与技术栈 → 全面拆解 → 与用户核对清单 → 按清单搭建（做不到要明说）→ 差异化改造+自查。**不要跳过拆解/核对直接写代码，也不要跳过差异化改造**——这两处正是"复刻不完整"和"复刻没特色"的解法。

## Phase 0：确认范围与技术栈

三件事先搞清，模糊开始只会返工：

- **输入来源**：URL（fetch_content 抓所有关键路由，不只首页，SPA 多抓状态）/ 截图或设计稿（read 逐张看；hover/动效/报错/加载**看不到，主动问用户，不要猜**）/ 仅关键词（先消歧义再 web_search 找官网与评测；**信息越少越要多轮调研，脑补是漏功能重灾区**）。详细处理见 `references/input-and-resume.md`。
- **复刻范围**：整站还是核心页面/某条流程？范围越大拆解越要系统化。
- **是否本地已有不完整复刻项目**：有则按 `references/input-and-resume.md` 的补全流程走（核心：仍针对原始目标独立拆解，再对照差距，不能只在现有项目认知边界内查漏）。

**技术栈**：默认 React + Tailwind，但动手前跟用户确认一次——内容型/营销型页面可能更适合静态 HTML/CSS/JS，用户也可能想贴近原栈。

## Phase 1：全面拆解目标（决定复刻完整性的核心）

把目标当机器拆，动手写代码前先产出**书面清单**（写出来，不能只在脑子里）——这是 Phase 2 核对和 Phase 5 自查的依据。

清单至少覆盖 9 维度：信息架构（页面/路由清单、导航层级）、页面级拆解（区块及顺序层级）、组件清单（含**全部状态**：默认/hover/激活/禁用/加载/空/报错/聚焦——最易漏）、内容与数据结构（每区块的数据字段）、交互与行为（点击/拖拽/动效/校验/搜索筛选排序/快捷键）、关键用户流程（注册/登录/下单等成功+失败+边界）、响应式行为（断点、移动端差异）、全局元素（header/footer/弹窗/toast/深浅模式）、次要功能（分页/无限滚动/空状态/404/tooltip/面包屑/cookie 条/骨架屏/无障碍）。分类型的逐项提示见 `references/decomposition-checklist.md`，列清单前先扫一遍。

发现信息缺失（截图没覆盖、URL 抓不到的动态内容）记"未知/待确认"留到 Phase 2 问，不要脑补。

## Phase 2：和用户核对清单，补齐盲区

原样呈现清单，明确问：有没有遗漏的页面/功能/状态？有没有用户不需要的部分（**用户主动精简 ≠ 复刻遗漏**，两种情况在 Phase 5 交付说明里要区分）？顺带再确认一次技术栈。这一步不能省——与其做完发现漏了返工，不如现在两分钟对齐，是全流程性价比最高的一步。

## Phase 3：按清单搭建，功能优先，不做隐性阉割

- 视觉/样式参考 `dj-design` 的设计规范；严格按 Phase 2 确认后的清单实现，**清单上的都要出现在产出里**，不因麻烦悄悄跳过或简化
- 技术限制做不到的（依赖真实后端、第三方支付网关等）**必须明确告知**"简化了什么、原因、替代方案"——阉割版的根源正是遇到麻烦悄悄跳过还不说
- 逐页/逐组件推进，做完就对照清单打勾，不留到最后一次性检查

## Phase 4：差异化改造（必做，不是可选项）

同时解决两件事，缺一不可：**去同质化**（降低版权/商标风险）+ **产品调性**（体现使用者风格）。具体手法见 `references/variation-playbook.md`，大方向：版式（网格/区块顺序/留白节奏/hero 构图/导航形式）、主题（整套配色对比关系/字体/圆角阴影，非只换主色）、品牌（占位名称/logo）。

**关键原则**：差异化改的是"表现层"不是"功能层"——Phase 2 确认过的信息架构、流程、组件覆盖保持完整，不能借差异化名义砍功能。建议准备 2-3 个方向（如极简白/深色科技感/温暖有机风）让用户选，不闷头自定。

## Phase 5：最终自查与交付

逐项对照 Phase 2 清单查覆盖（含次要功能与各状态）；技术简化项列清"哪里简化、为什么、影响"；总结差异化改动；产出文件放 outputs 目录并展示。

## Hard Rules

1. 5 个 Phase 必须走完，不能跳过 Phase 2（核对清单）或 Phase 4（差异化改造）
2. 拆解清单必须书面化，不能只放脑子里
3. 技术限制做不到的必须明确告知原因和替代方案，不能悄悄简化
4. 差异化不能以砍功能为代价——完整性和差异化互不冲突
5. 用户流程/敏感功能（注册/登录/支付）完整覆盖成功/失败/边界

## Gotchas

| Gotcha | 后果 | 预防 |
|---|---|---|
| 跳过 Phase 1/2 直接写 | 交付严重漏功能 | 列完清单对齐后再动代码 |
| 截图看不到的交互靠猜 | 交互与原版不一致 | 缺失部分主动问用户 |
| 遇麻烦悄悄简化不说明 | 用户拿到阉割版 | 做不到就明说，给替代方案 |
| 差异化改造砍了功能 | 功能残缺 | 改完对照 Phase 2 清单重过 |
| 关键词输入跳过调研列清单 | 脑补拆解一开始就偏 | 信息越少越多调研 |
| 补全任务只在现有项目范围查漏 | 没做过的功能继续被漏 | 针对原目标重新拆解再对照 |

# Codebase Design: 代码结构设计

决定代码放在哪、模块如何划分、接口如何定义。核心原则：**先设计两次**。

## 工作流

> 每步都要有**明确的产出**再进入下一步，不满足就回上一步补。

### 1. 理解上下文

**输入**：要解决的问题、现有代码库
**产出**：一段"现状理解"（问题是什么、现有结构、受影响模块）
**验收**：能说出改动会碰哪些文件，而非空泛"看代码"

- 要解决的问题/功能是什么？
- 现有的代码结构是怎样的？
- 哪些模块/文件会受影响？

### 2. 设计两次（Design It Twice）

**输入**：第 1 步的现状理解
**产出**：方案 A（第一版）+ 方案 B（最终版），各含"核心思路/为什么放弃/发现的约束"
**验收**：方案 A 被显式放弃，且写清了放弃原因

先设计第一个方案——不管多粗糙。然后**扔掉它**，从零开始设计第二个。

第一个方案的价值不是实现，是让你发现隐藏的假设和约束。第二个方案才是你要用的。

### 3. 评估方案

**输入**：方案 A/B
**产出**：选中一个方案作为最终方案
**验收**：未选中时用失败模式表处理（见下），不带着两个方案进下一步

```
方案 A（第一次设计）：
- 核心思路
- 为什么放弃
- 发现了什么约束

方案 B（最终方案）：
- 核心思路
- 模块划分
- 接口定义
- 文件放置
- 与现有结构的关系
```

### 4. 输出

**产出**：一份设计文档（结构/接口/数据流/影响范围）
**验收**：四要素齐全且不含实现细节

```markdown
## 设计方案

### 结构
<新增/改动的模块和文件>

### 接口
<对外暴露的接口签名>

### 数据流
<数据如何流转>

### 影响范围
<影响的现有模块和迁移路径>
```

## 失败模式

| 触发条件 | 一线修复 | 仍失败兜底 |
|---|---|---|
| 设计两次仍拿不定 | 用 `dj-reason` 认知矩阵对两方案做取舍 | 停下报告权衡点，请用户拍板 |
| 方案依赖未定的上游接口 | 先标注依赖为假设，不假装已定 | 转 `dj-grill` 对齐依赖 |
| 现有结构读不懂/过大 | 缩小到受影响模块局部理解 | 报告不确定性，不臆测全局 |

## 反例

| ❌ 不要做 | ✅ 正确做法 |
|---|---|
| 跳过第二次设计直接实现 | 第一版弃掉、第二版才是最终 |
| 没读现有结构就设计 | 先理解现有代码与影响面 |
| 输出里写实现细节 | 只给结构/接口/数据流/影响面 |
| 设计当成定稿不再评审 | 方案交用户确认后再进实现 |

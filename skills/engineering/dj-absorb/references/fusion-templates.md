# dj-absorb 模板与清单

本文件承载 dj-absorb 的卡片模板、融合方案模板与各 Phase 的详细确认/检查清单。SKILL.md 保留流程骨架；执行对应 Phase 需要模板时读本节。

## 1. Phase 0 自有项目快照要点

1. 浏览项目结构（目录布局、技术栈）
2. 现有组件体系（UI 组件库、自定义组件）
3. 现有设计语言/视觉规范（有设计规范或主题配置则读一遍）
4. 当前代码风格和命名约定
5. 现有架构模式（状态管理、数据流、路由方式）
6. 记录当前项目的"痛点"或"想改进的方向"（如有）

产出：自有项目快照文档（记录在对话或文件中，不必做成独立文件，但必须记录供 Phase 2 参考）。

## 2. Phase 0 吸收范围确认问题

- 具体看中这个目标的什么？（整个视觉风格？某个交互组件？数据展示方式？）
- 吸收到什么程度？（完全照搬再调风格，还是只借鉴思路自己重新实现？）
- 有没有已经有想法的融合方向？（或者愿意看建议？）
- 只吸收一个目标还是从多个目标中分别提取元素？

## 3. 候选元素卡片模板

```
## 候选元素卡片

来源：[目标名称]
元素类型：[UI 组件 / 交互模式 / 视觉语言 / 数据模型 / 架构模式 / 微交互]
描述：
吸收价值：[为什么这个值得吸收？比自有项目现有哪些优势？]
适配成本：[融入自有项目需要多大改动？]
冲突风险：[与自有项目现有风格/架构的冲突程度：高/中/低]
是否吸收：[是 / 否 / 待讨论]
理由：
```

筛选原则：
- **吸收价值 > 适配成本 + 冲突风险** 才吸收
- 同类元素来自多个目标时，优先吸收最有价值的，避免同类元素打架
- 技术栈不兼容、架构层冲突明显的，标记为"不适合吸收"并说明原因，而不是硬搬
- 拆解中发现信息缺失（截图看不到、URL 抓不到的动态交互），记"未知/待确认"，不在 Phase 2 之前脑补

## 4. 融合方案模板

对 Phase 1 中标记为"是"或"待讨论"的候选元素，逐个设计融合方案。这是"吸收融合"与"完整复刻"的关键区别——不是照搬，而是适配到自有项目。

```
## 融合方案：[元素名称]

### 适配分析
- 源实现方式：[目标中如何实现的]
- 自有项目现有方案：[目前有的 / 没有的情况]
- 适配方式：[直接搬代码再改 / 参考思路重新实现 / 部分参考 + 部分自定义]
- 改动范围：[涉及的文件和模块]

### 冲突解决
- 风格冲突：[与现有视觉风格是否一致？如何调和？]
- 架构冲突：[与现有数据流/状态管理是否兼容？]
- 命名冲突：[标识符与现有代码是否冲突？]

### 实现策略
- 改动方案：[具体怎么改]
- 新代码 vs 改现有代码：[是新增组件还是修改现有组件？]
- 依赖影响：[新增依赖？现有依赖的版本冲突？]

### 验证方式
- 验证清单：[怎么确认这次改动是正确的]
```

多目标融合的特殊处理：
- 从不同目标吸收的元素放到一起可能风格冲突——以自有项目为主体，调整外来元素匹配自有风格，而不是让自有风格匹配外来元素
- 两个目标对同类元素有不同方案时，选与自有项目更兼容的，或设计一个吸收两者优点且与自有一致的新方案

## 5. Phase 4 最终验证清单

1. **一致性检查**：新增/改动的代码是否和自有项目现有代码风格一致（命名、结构、注释风格）
2. **视觉一致性**：新引入的视觉元素是否与整体视觉风格协调（有主题配置则确认新元素用主题变量而非硬编码颜色）
3. **回归检查**：原有功能不受影响（跑测试、编译检查、手动检查受影响页面）
4. **多目标融合检查**：从多个目标吸收的不同元素之间是否协调，会不会看起来像拼凑的
5. **差异清单**：交付时清楚列出"从哪里吸收了哪些元素、做了什么适配改动"，方便项目成员了解
6. **用户确认**：展示成果，确认交付

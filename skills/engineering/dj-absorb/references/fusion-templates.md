# dj-absorb 模板与清单

本文件承载 dj-absorb 的卡片模板、融合方案模板与各 Phase 的详细确认/检查清单。SKILL.md 保留流程骨架；执行对应 Phase 需要模板时读本节。

## 1. Phase 0 自有项目快照要点

1. 浏览项目结构（目录布局、技术栈）
2. 现有组件体系（UI 组件库、自定义组件）
3. 现有设计语言/视觉规范（有设计规范或主题配置则读一遍）
4. 当前代码风格和命名约定
5. 现有架构模式（状态管理、数据流、路由方式）
6. 记录当前项目的"痛点"或"想改进的方向"（如有）

产出：自有项目快照文档（记录在对话或文件中，不必做成独立文件，但必须记录供 Phase 2 参考）。

## 2. Phase 0 吸收范围确认问题

- 具体看中这个目标的什么？（整个视觉风格？某个交互组件？数据展示方式？）
- 吸收到什么程度？（完全照搬再调风格，还是只借鉴思路自己重新实现？）
- 有没有已经有想法的融合方向？（或者愿意看建议？）
- 只吸收一个目标还是从多个目标中分别提取元素？

## 3. 候选元素卡片模板

```
## 候选元素卡片

来源：[目标名称]
元素类型：[UI 组件 / 交互模式 / 视觉语言 / 数据模型 / 架构模式 / 微交互]
描述：
吸收价值：[为什么这个值得吸收？比自有项目现有哪些优势？]
适配成本：[融入自有项目需要多大改动？]
冲突风险：[与自有项目现有风格/架构的冲突程度：高/中/低]
是否吸收：[是 / 否 / 待讨论]
理由：
```

筛选原则：
- **吸收价值 > 适配成本 + 冲突风险** 才吸收
- 同类元素来自多个目标时，优先吸收最有价值的，避免同类元素打架
- 技术栈不兼容、架构层冲突明显的，标记为"不适合吸收"并说明原因，而不是硬搬
- 拆解中发现信息缺失（截图看不到、URL 抓不到的动态交互），记"未知/待确认"，不在 Phase 2 之前脑补

## 4. 融合方案模板

对 Phase 1 中标记为"是"或"待讨论"的候选元素，逐个设计融合方案。这是"吸收融合"与"完整复刻"的关键区别——不是照搬，而是适配到自有项目。

```
## 融合方案：[元素名称]

### 适配分析
- 源实现方式：[目标中如何实现的]
- 自有项目现有方案：[目前有的 / 没有的情况]
- 适配方式：[直接搬代码再改 / 参考思路重新实现 / 部分参考 + 部分自定义]
- 改动范围：[涉及的文件和模块]

### 冲突解决
- 风格冲突：[与现有视觉风格是否一致？如何调和？]
- 架构冲突：[与现有数据流/状态管理是否兼容？]
- 命名冲突：[标识符与现有代码是否冲突？]

### 实现策略
- 改动方案：[具体怎么改]
- 新代码 vs 改现有代码：[是新增组件还是修改现有组件？]
- 依赖影响：[新增依赖？现有依赖的版本冲突？]

### 验证方式
- 验证清单：[怎么确认这次改动是正确的]
```

多目标融合的特殊处理：
- 从不同目标吸收的元素放到一起可能风格冲突——以自有项目为主体，调整外来元素匹配自有风格，而不是让自有风格匹配外来元素
- 两个目标对同类元素有不同方案时，选与自有项目更兼容的，或设计一个吸收两者优点且与自有一致的新方案

## 5. Phase 4 最终验证清单

1. **一致性检查**：新增/改动的代码是否和自有项目现有代码风格一致（命名、结构、注释风格）
2. **视觉一致性**：新引入的视觉元素是否与整体视觉风格协调（有主题配置则确认新元素用主题变量而非硬编码颜色）
3. **回归检查**：原有功能不受影响（跑测试、编译检查、手动检查受影响页面）
4. **多目标融合检查**：从多个目标吸收的不同元素之间是否协调，会不会看起来像拼凑的
5. **差异清单**：交付时清楚列出"从哪里吸收了哪些元素、做了什么适配改动"，方便项目成员了解
6. **用户确认**：展示成果，确认交付

## 6. 四态重验细则（输入含调研报告/差距清单时）

筛选表加一列「自有项目实际代码状态」，逐条判定：

- **已有**：差距已被后续开发实现，不再需要
- **真实差距**：确未实现且仍值得吸收
- **前提失效**：建议的前提已随架构路线变更失效（如项目已从 CLI 迁移到纯 skill 架构）
- **不适合**：与当前技术栈/架构冲突

报告结论会过时：差距可能已被后续开发实现，建议的前提也可能随架构路线变更而失效（实证：12 条旧报告建议中 6 条已实现、2 条前提失效、仅 4 条真实差距）。直接采信会把已实现功能当新需求重做，或把已放弃路线的机制重新引入。

## 7. 多目标并行调研（外部目标为多个仓库/项目时）

每个目标派一个**只读研究子代理**并行拆解，提示词四要素：

1. **自有项目现状快照**（架构/技术栈/已有机制，供其判定适配性）
2. **已覆盖清单**（旧分析报告已挖过的机制，防止重复挖掘）
3. **只读约束**（只研究、不修改任何文件）
4. **按候选元素卡片格式输出**（含源文件路径）

主 session 只做归并去重、按主题分组与冲突评估，不亲自逐仓深挖。

## 8. 技能定位与主要风险（正文迁入）

**复刻**（`dj-remix`）整站抄来再差异化；**吸收融合**（本 skill）以自有项目为主体提取特定元素增量融入。主要风险不是漏功能，而是：**风格冲突**、**架构不匹配**（外部模式在自有技术栈下不适用）、**过度吸收**（拼凑品）、**选择性偏误**（只看好部分，忽略设计在源项目的上下文约束——交互简洁可能是后端强大撑的）、**入口失配**（融合产物不被入口路由触达，成了永远不会执行的死技能）。

## 9. 强度等级三档定义（正文迁入）

lite（1-2 个明确元素快速落地，跳过完整拆解）/ full 默认（全 Phase）/ ultra（多目标、架构级吸收，加冲突分析与替代方案评估）。

## 10. Phase 0 摸底细则（正文迁入）

拆解外部目标前先搞清自有项目现状：快照（结构/组件体系/设计规范/代码风格/架构/痛点）；外部目标确认（URL fetch_content / 截图 read / 关键词先消歧义再 web_search）；**吸收范围确认**（看中什么/到什么程度/融合方向/单多目标）。

**摸底以源码为准，不以 README 为准**：README 可能落后代码多个版本（实证：README 停 v0.1.x 而代码已 v0.2.0，差距分析 78% 误报）。功能现状盘点基于实际源码（组件目录/hooks/lib 真实实现），README 只作线索不作结论。

## 11. Phase 1 拆解视角与候选卡片（正文迁入）

吸收视角（而非复刻视角）系统化拆解——关注"有什么值得借鉴的元素"。每个候选记一张**卡片**（来源/类型/价值/成本/冲突风险/是否吸收/理由）。

## 12. 调研报告重验与并行调研（正文迁入）

两条硬纪律：**输入含调研报告/差距清单时逐条对照源码重验**——四态判定（已有/真实差距/前提失效/不适合），直接采信会把已实现功能当新需求重做、把已放弃路线的机制重新引入；**多目标并行调研**——每目标派一个只读研究子代理并行拆解，主 session 只做归并去重与冲突评估。

## 13. 融合方案要素（正文迁入）

对标记"是/待讨论"的候选逐个设计融合方案——不是照搬而是适配。方案含适配分析（源实现/现有方案/适配方式/改动范围）、冲突解决（风格/架构/命名）、实现策略（新增 vs 修改/依赖影响）、验证方式。多目标融合以自有项目为主体，外来元素适配自有风格，反之不行。

## 14. Phase 3 落地纪律（正文迁入）

核心原则：**一条一条做，做完一条验证一条，不堆在一起验收**。每次只实现一个元素；实现前确认不依赖其他未实现元素（有依赖先实现被依赖的）；每条按 Phase 2 验证方式快速验证；视觉改动参考 `dj-design` 一致部分；实现困难（技术限制/冲突超预期）暂停评估——降要求/换方式/放弃。**Phase 3 发现 Phase 2 方案有问题不硬撑，回 Phase 2 调整再继续。**

## 15. Phase 4 验证要点（正文迁入）

全部完成后整体验证：一致性、视觉一致性（主题变量非硬编码）、回归检查、多目标协调、差异清单、用户确认。

## 16. Gotchas 长条目（正文迁入）

| Gotcha | 预防 |
|---|---|
| 懒得改方案直接搬代码 | 融合方案阶段做好适配设计 |
| 从多目标吸收同类元素 | 优先兼容好的，或设计统一方案 |
| Phase 3 遇冲突不回头 | 暂停，回 Phase 2 调整 |
| "借鉴这个"不指明具体元素 | Phase 0 追问看中什么 |
| 采信调研报告差距结论不重验 | 逐条对照源码四态核实 |
| 按 README 盘点功能现状 | 以源码为准，README 只作线索 |
| 把"本轮不做/YAGNI 取舍"归入"已覆盖" | 四态显式分类：**已有/真缺口/边界项/不适用**——"不做"≠"已有"，混类漏报真缺口 |
| 效果不如外部参考，却只补工程严谨性 | **效果是硬指标**：机制层"已强于"≠效果。当自有项目效果不如外部参考时，不要轻信报告里"原则层已强于"的结论，按实际执行架构反推根因——真实差距常在结构（并行调度/重规划/收敛证据/执行层协作），而非计量/索引/状态机这类严谨性；并核对提示词宣称的能力（如 parallelizable/delegation）与调度器实际行为是否一致，自相矛盾是效果落空的常见根因 |

## 17. 五步流程概览与经典短 Gotchas（正文迁入）

五步：摸底 → 拆解与筛选（有框架地挑）→ 融合方案（逐候选适配+评冲突）→ 落地实现（一条一条做）→ 最终验证。

| Gotcha | 预防 |
|---|---|
| 跳过 Phase 0 直接拆解 | 先摸底再拆解 |
| 只看想借鉴部分忽略上下文约束 | 拆解时同时关注依赖条件 |
| 一次吸收太多元素 | 3-5 个后做一致性检查 |
| 忽略自有项目风格 | 每元素做冲突分析 |

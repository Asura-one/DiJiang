| 项目 | 内容 |
|---|---|
| **Outcome** | 外部精选元素增量融入自有项目，风格/架构一致，无回归 |

# Absorb: 选择性吸收融合

## 要解决的问题

"借鉴"≠"复刻"：**复刻**（`dj-remix`）把目标整个抄过来做差异化，产出新 standalone 项目；**吸收融合**（本 skill）以自有项目为主体，有选择地提取外部特定元素**增量融入**已有代码库。主要风险不是漏功能，而是：**风格冲突**（与自有视觉/代码风格不统一）、**架构不匹配**（外部模式在自有技术栈下不适用）、**过度吸收**（项目变拼凑品）、**选择性偏误**（只看好部分，忽略设计在源项目中的上下文约束——比如交互简洁是因为后端强大）。

五步：摸底 → 拆解与筛选（有框架地挑，不凭第一印象）→ 融合方案（逐候选设计适配+评冲突）→ 落地实现（一条一条做）→ 最终验证。

## 强度等级

| 等级 | 适用场景 |
|------|----------|
| **lite** | 只吸收 1-2 个明确元素（如"借鉴配色"），快速落地，跳过 Phase 1 完整拆解 |
| **full**（默认）| 标准流程，完整走全部 Phase |
| **ultra** | 多目标融合、架构级吸收（数据模型/状态管理模式），增加冲突分析与替代方案评估 |

## Phase 0：摸底

拆解外部目标前先搞清自有项目现状——不知道自己项目长什么样，就不可能设计出匹配的融合方案。自有项目快照（结构/组件体系/设计规范/代码风格/架构模式/痛点，要点见 references/fusion-templates.md）；外部目标确认（URL 用 fetch_content / 截图用 read / 关键词先消歧义再 web_search，多目标分别确认）；**吸收范围确认**（看中什么/吸收到什么程度/融合方向/单目标还是多目标，问题清单见 references）。

## Phase 1：拆解与筛选

对每个外部目标做吸收视角（而非复刻视角）的系统化拆解——不关心"哪些功能需要全量复制"，关注"有什么值得借鉴的元素"。拆解维度参考 `references/absorption-checklist.md`。每个候选元素记录一张**卡片**（来源/类型/描述/吸收价值/适配成本/冲突风险/是否吸收/理由，模板见 references/fusion-templates.md）。

## Phase 2：融合方案

对标记"是"或"待讨论"的候选元素逐个设计融合方案——不是照搬，而是适配到自有项目。方案含适配分析（源实现/现有方案/适配方式/改动范围）、冲突解决（风格/架构/命名）、实现策略（改动方案/新增 vs 修改/依赖影响）、验证方式（模板见 references）。多目标融合时以自有项目为主体，外来元素适配自有风格，反之不行。

**🔴 🛑 STOP：展示所有融合方案给用户确认。**用户说"继续"再进 Phase 3；用户可能调整范围、修改方案或放弃某些元素。

## Phase 3：落地实现

按确认后的方案逐条实现，核心原则：**一条一条做，做完一条验证一条，不堆在一起验收**。每次只实现一个元素；实现前确认它不依赖其他未实现元素（有依赖先实现被依赖的）；每完成一条按 Phase 2 的验证方式快速验证；视觉改动参考 `dj-design` 与自有项目一致的部分；遇到实现困难（技术限制、冲突超预期）暂停评估——降适配要求/换实现方式/放弃该元素。**Phase 3 发现 Phase 2 方案有问题时不硬撑原方案，回 Phase 2 调整再继续。**

## Phase 4：最终验证

全部元素完成后整体验证（六项清单见 references/fusion-templates.md）：一致性（代码风格）、视觉一致性（主题变量而非硬编码）、回归检查、多目标协调检查、差异清单、用户确认。

## Hard Rules

1. 5 个 Phase 必须走完，不能跳过 Phase 0（摸底）或 Phase 2（融合方案设计）
2. 拆分清单和融合方案必须书面化，不能只在脑子里
3. Phase 2 方案必须经用户确认才进 Phase 3
4. 技术限制或不兼容必须明确告知原因和替代方案，不能悄悄简化
5. 不能以"借鉴"为名完整复刻整个页面/功能——那是 `dj-remix` 范畴
6. 不能破坏自有项目风格/架构一致性——每引入一个外来元素都确认与现有部分匹配
7. 多目标吸收时自有项目是主体，外来元素适配自有风格，反之不行
8. 每实现一个元素验证一个元素，不堆到 Phase 4 一次性检查

## Gotchas

| Gotcha | 预防 |
|---|---|
| 跳过 Phase 0 直接拆解 | 先摸底再拆解 |
| 只看想借鉴部分忽略上下文约束 | 拆解时同时关注依赖条件 |
| 一次吸收太多元素 | 3-5 个后做一致性检查 |
| 忽略自有项目风格 | 每元素做冲突分析 |
| 懒得改方案直接搬代码 | 融合方案阶段做好适配设计 |
| 从多目标吸收同类元素 | 优先兼容性好的，或设计统一方案 |
| Phase 3 遇冲突不回头 | 冲突超预期暂停，回 Phase 2 调整 |
| "借鉴这个"不指明具体元素 | Phase 0 追问清楚看中什么 |
